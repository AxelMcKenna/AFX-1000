# Four-cap receiving repair — isolated restart

The derived scene moves only C4/C5/C31/C32 by the actual native 0.6 mm v change.
The other receiving boxes, tails, mates and allowances are preserved.

The first Mac native batch launched47
OpenSCAD processes, each aborting at startup with SIGABRT and the Qt error
`Incompatible processor ... neon`. The batch incorrectly continued after each
fatal exit. These are execution failures, not 47 geometric collisions. The raw
logs and invalid execution report are retained in the
[verified failed-batch archive](../../qualification_reviews/cleanup_restart_20261030/failed-native-batch.zip).
No successful mesh was generated by that batch.

Mac native CAD launches remain stopped by
[`NATIVE-CAD-STOP.json`](../../../../validation/board-qualification/NATIVE-CAD-STOP.json).
Do not run the historical parent replay command for this successor. `run.py`
checks the stop marker before any process launch and stops immediately on a
fatal exit or timeout. The guard was tested with a mocked launcher and started
zero native applications. It has not been tested by reopening OpenSCAD.

The [isolated Linux restart](../../controlled_restart/README.md) now freshly
passes the NF265 rear-tail/component collision check and its actual PCB positive
control, after a known1.5mm³ Boolean probe. This closes the tested four-cap
rear-tail receiver conflict for the captured scene. It does not inherit or
establish the rest of the47-case matrix, exact production part heights, other
connector clearances, complete harness fit or physical qualification.

The [incident record](../../qualification_reviews/openscad_repeated_abort_20261030/incident.json)
records the failures and correction. No physical or fabrication approval exists.
